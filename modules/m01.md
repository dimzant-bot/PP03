# Модуль 1. Применение технологии исследования репозитория проекта

**16 ч · 03.11–05.11 · ПК 3.1, ПК 3.3**

**Цель:** разобраться в чужом проекте по его репозиторию и составить паспорт проекта.
**Результат идёт в:** все следующие модули работают с этим проектом; паспорт — основа введения итогового отчёта.

## Шаг 0. Подготовка (первый день)

1. Инструктаж по ТБ, подпись в карточке.
2. Git, VS Code, Python 3 установлены. Проверка:
   ```
   git --version
   python --version      (Linux/macOS: python3 --version)
   ```
3. Git настроен:
   ```
   git config --global user.name "Иванов Иван"
   git config --global user.email "ivanov@example.com"
   git config --global core.autocrlf input      (Windows: true)
   ```
4. SSH-ключ создан и добавлен в аккаунт GitHub / GitFlic:
   ```
   ssh-keygen -t ed25519 -C "ivanov@example.com"
   ```
   Публичный ключ — файл `~/.ssh/id_ed25519.pub` → Settings → SSH keys. Приватный ключ никому не отправлять.

## Шаг 1. Выбор и получение проекта

1. Выберите проект (требования — в README репозитория практики) и согласуйте с руководителем.
2. Сделайте форк (кнопка Fork) или импорт (New → Import repository) в свой аккаунт.
3. Клонируйте **свой** форк:
   ```
   git clone git@github.com:ВАШ_ЛОГИН/ПРОЕКТ.git
   cd ПРОЕКТ
   ```
4. Скопируйте в проект шаблоны практики (из папки `pp03-ispo332`):
   ```
   powershell -ExecutionPolicy Bypass -File tools\install.ps1 C:\путь\к\ПРОЕКТ     (Windows)
   bash tools/install.sh ~/путь/к/ПРОЕКТ                                        (Linux/macOS)
   ```
5. Создайте ветку модуля и первый коммит:
   ```
   git switch -c practice/m01
   git add practice .github
   git commit -m "chore: add practice skeleton"
   git push -u origin practice/m01
   ```
6. Заполните шапку `practice/README.md`.

## Шаг 2. Структура каталогов

```
git ls-files | head -50                         (Windows PowerShell: git ls-files | Select-Object -First 50)
tree -L 2 -I node_modules                       (Windows: tree /F | more)
```
Заполните таблицу «Структура каталогов» в `passport.md`: каждая папка верхнего уровня и важные файлы
(`package.json`, `composer.json`, `requirements.txt`, `Dockerfile`, `.env.example`, миграции).

## Шаг 3. Стек и зависимости

1. Объём кода по языкам:
   ```
   python ПУТЬ\pp03-ispo332\tools\metrics.py .
   ```
2. Откройте файл зависимостей и выпишите 10–15 главных пакетов: зачем каждый нужен (смотрите описание на npmjs.com / pypi.org / packagist.org).
3. Определите СУБД: ищите `DATABASE_URL`, `DB_CONNECTION`, `.env.example`, файлы миграций.

## Шаг 4. История репозитория

```
python ПУТЬ\pp03-ispo332\tools\repo_stats.py . --out practice/m01/repo-stats.md
git log --oneline --graph --all --decorate -n 40        <- скриншот в отчёт
git shortlog -sn --all
git branch -a
git tag
git blame -- путь/к/важному/файлу | head -40
git log --follow --oneline -- путь/к/важному/файлу
```
Вопросы, на которые должен ответить раздел «История»:
- Проект живой или заброшен? (даты первого и последнего коммита)
- Один автор или команда?
- Какие файлы меняются чаще всего — это обычно ядро логики или источник проблем.
- По `git blame`: кто и когда писал ключевой файл, есть ли «заплатки» поверх старого кода.

## Шаг 5. Запуск

Запустите проект по README. Записывайте каждую команду, которая сработала, в раздел «Запуск».
Не запускается — это нормальная находка ревьюера: опишите, что не так, и как исправили (версия Node, нет `.env`, нет миграций).
Если README неполный — допишите его и закоммитьте (`docs: дополнена инструкция запуска`).

## Подсказки

- `.env` с паролями **не коммитить**. Если проекту нужен `.env`, создайте его из `.env.example`.
- Если проект огромный (> 50 тыс. строк) — согласуйте с руководителем, какую часть исследуете.
